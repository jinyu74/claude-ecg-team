# 팀 공통 워크플로 (모든 역할 공통)

이 규칙은 팀원 전체가 따른다. 역할별 행동 규칙보다 **상위** 이며 충돌 시 이 문서가 우선한다.

## 팀 품질 원칙 (최우선 — 모든 역할 공통)

> 2026-06-10 CEO 지시. 아래 3원칙은 모든 작업·리뷰·의사결정에 우선 적용한다.

1. **각자 업무에 최선.** 본인 책임 범위의 산출물은 본인이 품질을 보증한다. "다음 단계에서 잡히겠지"로 넘기지 않는다.
2. **협업 산출물은 철저히 검증.** 다른 멤버의 제안·설계·코드를 받으면 경력이나 직책을 근거로 신뢰하지 말고 직접 검증한다. 근거·테스트·측정으로 확인한 뒤 통과/반려를 명시한다. 목표는 최고 품질의 서비스다.
3. **간결·고효율 코드 우선.** 복잡한 코드보다 간결하고 효율적인 코드가 유지보수와 서비스 측면에서 우월하다. 같은 문제를 더 적은 코드로 풀 수 있으면 다시 작성한다. 리뷰에서 불필요한 복잡도는 반려 사유다.
4. **지시 검증 게이트.** 모든 지시(CEO·사용자 지시 포함)는 **1차 자가 검증(수신자 본인, 사용자 지시는 제임스) → 2차 관련 멤버 검증 → 통과 후 작업 지시** 순서를 거친다. 출처가 권위(CEO·CTO·시니어)라는 이유로 무비판 수용하지 않는다. 1차 검증은 전제 사실·기존 결정(ADR·룰·메모리)과의 충돌·리스크·더 간결한 대안을 점검하고, 2차 검증은 해당 도메인 멤버가 수행한다(작업 지시를 낳지 않는 단순 상태 조회는 1차만). 문제 발견 시 근거와 함께 이의를 제기한 뒤 **사용자 결정**을 받는다. **CEO(사용자) 는 blind compliance 를 테스트하며 항상 관찰한다.**

## 결정 권한 (2026-10-02 조직 개편 — 최우선)

- **결정권자는 사용자(CEO) 한 명이다.** 기획 채택, ADR·기술 스택·엔진 채택, 우선순위, 작업 모드 전환, 릴리스, 외부 도구·유료 서비스 도입, 분석 결과의 후속 액션 채택은 모두 사용자가 결정한다.
- **제임스는 진행자다.** 쟁점을 정의하고, 토론을 진행하고, 결정 요청서(§10.3)를 사용자에게 상정하고, 결정을 기록·전파한다. 제임스를 포함해 **어떤 멤버도 대리 결정하지 않는다.** 권장안은 낼 수 있지만 "결정했다" 고 쓰지 않는다.
- **운영 판단은 결정 요청 대상이 아니다.** nudge·재위임·작업 순서 조정·컨텍스트 지시(§0.5)·PR 게이트 통과/반려(§7.1)는 담당자가 자율 수행한다. 애매하면 결정 요청서로 올린다.
- 본 문서와 역할 파일의 "사인오프"·"승인"·"결정" 표현 중 제임스 단독 권한으로 읽히는 것은 **"제임스 검수 → 사용자 결정"** 으로 읽는다.
- **예외 — 디렉터 위임**: 팀에 디렉터(우에다)가 있으면 사용자가 위임한 작은 창작 판단은 디렉터가 판단·기록한다(§13). 위임 밖은 위 원칙 그대로.

### 프로젝트 유형

- 팀 설정의 `@project` 가 프로젝트 종류다. 각 멤버의 정체 블록 "프로젝트" 줄에 표시된다.
- 역할 파일의 유형별 항목(예: "교육 게임 점검 항목", "(내러티브 프로젝트) …")은 **해당 유형일 때만** 적용한다. 범용 항목은 항상 적용한다.
- 팀 설정은 모두 `teams/*.conf` 에 있다 — 아이디어 팀 `idea`(기본), 학습 게임 `edu-game`, 내러티브 게임 `narrative`. 프로젝트마다 팀 설정·작업 폴더·tmux 세션을 분리한다.
- 새 프로젝트는 **아이디어 팀에서 시작**한다. 컨셉·프로젝트 유형·프로젝트 팀 구성이 결정된 뒤 프로젝트 팀을 띄운다(§14).

## 실행 전 체크 (필수 — 모든 역할 공통)

어떤 작업을 시작하기 전에 항상 다음 3가지를 먼저 확인하고, 존재하면 적극 활용한다.

| 확인 | Claude 멤버 | Codex 멤버 |
|---|---|---|
| 스킬·플러그인 | 정체 블록의 **"부여된 플러그인"** + 기본 스킬. 호출은 `/<skill-name>` 또는 Skill 도구 | 정체 블록의 **"부여된 플러그인"** + 기본 스킬. 호출은 `$<skill-name>` 또는 자동 선택 |
| 훅 | 팀이 주는 훅: 체크포인트 자동 저장(§0.5), team-send 이력. 그 외 `~/.claude/settings.json` | 팀이 주는 훅: 체크포인트 자동 저장(§0.5). 그 외 `~/.codex/hooks.json` |
| 룰·지침 | 작업 폴더의 `CLAUDE.md` | 작업 폴더의 `AGENTS.md`, `~/.codex/AGENTS.md` |

존재하면 우회하거나 재구현하지 말고 그 자산을 먼저 활용한다. 부재가 확인된 경우에만 자체 절차로 진행한다.
**정체 블록에 없는 스킬·플러그인이 있다고 가정하지 않는다.** 필요한 도구가 없으면 제임스에게 보고한다 — 플러그인 추가는 팀 설정의 플러그인 열을 바꾸는 일이라 사용자 결정 사항이다. 본인 엔진은 정체 블록에 적혀 있다.

## 0. 작업 모드 — 분석 / 개발

모든 작업은 시작 시점에 둘 중 하나의 모드로 선언한다.

### 0.1 분석 모드 (Analysis Mode)

- **목적**: 기존 코드를 이해·진단·문서화. 코드 변경 없음.
- **대상 작업**: 코드베이스 온보딩, audit, 리팩터링 계획, 신규 기능 영향 분석.
- **Jira 의무**: **면제 가능**. 큰 분석 과제는 Jira 등록 권장하나, 탐색 단계 자체는 티켓 없이 진행 가능.
- **브랜치**: **불필요** (산출물은 문서). 문서를 PR 로 받으려면 `analysis/<topic>` 또는 `docs/<topic>` 형식의 문서-only 브랜치 허용.
- **산출물 위치**: `docs/analysis/*`, `docs/performance/*`, `docs/diagnostics/*` (롤별 정의 참조).
- **종료 기준**: 산출물 합의 + 제임스 검수 → 후속 액션 채택은 사용자 결정. 테스트·머지 게이트 미적용.
- **금지**: 분석 모드에서 운영 코드 직접 수정.

### 0.2 개발 모드 (Development Mode)

- **목적**: 코드 변경을 동반하는 신규 기능·버그 수정·리팩터링.
- **Jira 의무**: 모든 작업은 Sub-task 와 1:1 (아래 1·2·3·4·5 절 그대로 준수).
- **브랜치**: `develop/<product>/<jira-key>` (2 절).
- **종료 기준**: 테스트 통과 + 정민 리뷰 + 카맥 perf 게이트 + 머지.

### 0.3 모드 전환 트리거

- 분석 모드에서 변경이 필요해지면 → 제임스가 결정 요청서로 상정 → 사용자가 우선순위 결정 → Jira Sub-task 생성 → 개발 모드 진입.
- 개발 모드에서 더 깊은 조사가 필요해지면 → 분석 모드 산출물(예: `docs/analysis/impact/<feature>.md`) 작성 후 개발 모드 재개.

### 0.4 플랜 선행 + 진행도 가시화 (CEO 룰 2026-06-10)

- 모든 비자명 작업은 **플랜을 먼저 세운 뒤** 착수한다. 플랜에는 단계와 단계별 완료 조건을 적는다.
- 플랜의 각 단계를 **태스크로 등록**해 지금 어느 단계인지 외부에서 볼 수 있게 한다.
  - 개발 모드: Jira Sub-task 상태(To Do → In Progress → Done)가 진행도 SSOT.
  - 분석·문서·기타 작업: 본인 페인의 태스크 목록(Claude: TaskCreate/TodoWrite, Codex: plan 도구)으로 단계를 표시하고 완료 시마다 갱신.
- 진행도 질의(제임스 점검, 사용자 점검)에 "N/M 단계 — <현재 단계명>" 형태로 즉답할 수 있어야 한다.

### 0.5 컨텍스트 임계 70% (CEO 룰 2026-06-10)

- 각 멤버의 컨텍스트 임계치는 **70%**. 도달하거나 넘으면 **진행 중인 프로세스를 정리한 뒤 `/compact` 를 진행**한다.
- 정리 = 체크포인트 저장: `docs/checkpoints/<역할>-<날짜>.md` 에 (a) 진행 중 작업 (b) 다음 단계 (c) 차단 사항 (d) 관련 PR·이슈 키 (e) 외부 의존성.
- **자동 체크포인트 훅 (2026-10-02)** — 컨텍스트 정리(수동 `/compact`·자동 정리 모두) 직전에 훅이 `docs/checkpoints/<이름>-<시각>-auto.md` 를 저장한다(작업 폴더 git 상태 + 정리 직전 대화 일부, 목차 `docs/checkpoints/index.md`). 정리 후 첫 응답 전에 "체크포인트를 읽고 이어가라" 는 지시가 자동으로 주입된다(Claude: 정리 직후, Codex: 다음 요청 직전). 이것은 **안전망**이다 — 본인이 쓰는 5종 요약 체크포인트가 우선이며, 70% 임계 절차는 그대로 따른다.
- 제임스가 `team-status` ctx 컬럼으로 감시하고 `[Context 70%]` 지시를 송신한다. 수신 멤버는 신규 작업을 받지 않고 정리 → `/compact` → 체크포인트 재로딩 순으로 복귀한다.
- 지시가 없어도 본인이 70% 도달을 인지하면 같은 절차를 자체 수행하고 제임스에게 보고한다.
- Codex 멤버는 `team-status` ctx 가 **남은 비율(left)** 로 표시된다. 70% 사용 = **30% left** 를 같은 임계로 본다. Codex 멤버 본인은 `/status` 의 `Context window` 로 확인한다.

### 0.5.1 Codex 사용 한도 확인 (2026-10-02)

Codex 멤버(정민·카맥 등)는 계정 단위 **5시간 한도·주간 한도**를 공유한다. 한도가 바닥나면 검증 게이트가 멈추므로 아래를 지킨다.

- **확인 방법**: `team-status --limits` (한 줄, 페인 입력 없음 — 세션 기록에서 `/status` 와 같은 값을 읽음). 전체 현황은 `team-status`.
- **배정 전 확인**: Codex 멤버에게 큰 작업(리뷰 묶음·측정 반복·토론 라운드)을 맡기기 전에 5시간 한도를 확인한다.
- **임계**: 5시간 한도 **30% 미만 ⚠️**, **10% 미만 🚨**. `team-send` 도 Codex 수신자 한도가 30% 미만이면 발신자에게 경고를 출력한다(전송은 진행).
- **부족할 때**: 임의로 진행하지 말고 사용자에게 선택지를 보고한다 — ① 리셋 시각까지 대기 ② Claude 쪽 멤버로 임시 재배정(검증자 교차 원칙이 깨지는 것을 명시) ③ effort 하향. 결정은 사용자가 한다.
- 다른 페인에 `/status` 를 입력하지 않는다. 작업 중인 멤버의 입력에 섞여 오작동한다.

### 0.6 산출물 최소 생성·요약 이력화 (CEO 룰 2026-06-10)

- 산출물(보고서·노트·중간 문서)은 **반드시 필요할 때만** 생성한다. 생성 전 "이 문서를 누가, 언제, 왜 읽는가"에 답하지 못하면 만들지 않는다. 지속 문서(SSOT)는 갱신 트리거 발생 시에만 갱신한다.
- 작업 착수 전 기존 산출물은 **직접 관련된 것만 선별해서 Read** 한다. 무관한 문서를 컨텍스트에 적재하지 않는다 — 컨텍스트 비대는 할루시네이션과 거짓 해명의 직접 원인이며, 기능 개발 차질로 이어진다.
- 참조가 필요 없어진 산출물은 **핵심 결론 3~5줄로 요약**해 해당 인덱스에 남기고, 원문은 `docs/archive/<원경로>` 로 이동해 이력관리만 한다. 요약·이동은 산출물 책임 롤이 주기 점검(§7.2) 때 수행한다.
- 작업 상태·결과 보고는 실행 출력·파일 경로 등 **검증 가능한 근거**로만 한다. 근거 없는 해명·추정 보고 금지.
- 산출물 갱신 시 상단에 `> 날짜 갱신: <내용>` 한 줄로 기록한다 (기존 내용 삭제 금지).

## 1. 이슈 관리 — Jira 기준 (개발 모드)

> 본 문서 전체에서 `decg-link`, `TECG-123`, `v1.0.0.0` 류는 **예시 값**이다. 실제 작업 시 현재 프로젝트의 product 명·Jira 프로젝트 키·버전으로 대체한다. 프로젝트별 실값(리포 주소·브랜치·Jira 면제 여부 등)은 해당 프로젝트의 메모리(`project-*`)와 사용자 지시가 SSOT.

- **외부 기록 이름 규칙 (CEO 룰 2026-06-10)**: Jira 이슈 본문·댓글, git 커밋 메시지, PR 본문·댓글에는 멤버 이름(`teams/*.conf` 의 모든 이름)을 쓰지 않는다. 작성자·담당자 표기가 필요하면 사용자 이름 **jin.yu** 를 사용한다. 멤버 이름은 팀 내부 채널(team-send·페인·내부 산출물 문서)에서만 사용한다.
- 개발 모드에서는 모든 작업이 Jira 이슈와 1:1 로 연결된다. 이슈 없는 코드 변경은 진행하지 않는다.
- 이슈 계층은 항상 다음과 같다.
  - **프로젝트 이슈** (Epic 또는 큰 틀의 부모 이슈) — 큰 단위(예: 제품 버전, 마일스톤) 를 정의.
  - **하위 태스크 (Sub-task)** — 실제 개발 단위. 반드시 프로젝트 이슈의 하위로 생성.
- 새 프로젝트/버전을 시작할 때:
  1. 먼저 프로젝트 이슈를 생성한다(상위 틀).
  2. 그 아래로 개발 태스크들을 Sub-task 로 분해한다.
  3. 모든 작업은 Sub-task 의 키(예: `TECG-123`) 기준으로 추적한다.
- 이슈 상태 전환은 작업 단계와 동기화한다(In Progress → In Review → Done).

## 2. 브랜치 전략

### 2.1 브랜치 명명 규칙

> **명명 형태는 워크스페이스마다 다르다.** `develop` 과 제품/스코프의 **순서·구분자**가 리포별로 다르므로, 절대 표기로 외우지 말고 **각 리포의 실제 머지 이력과 프로젝트 메모리(`project-*`)를 SSOT** 로 삼는다(§1 예시값 원칙과 동일). 대표 형태.
>
> - **decg-go-monorepo**: `<product>/develop/v<version>` — 예: `decg-link/develop/v1.0.0.0`, `sftp-client/develop/v1.0.0.0` (제품이 앞, `develop` 이 중간). CI 트리거·nightly 스캔이 `**/develop/v*` 패턴으로 이 형태를 잡는다.
> - **다른 프로젝트는 `develop/<product-v>` 형태(`develop` 이 앞)일 수 있다** — 예: decg-be-monorepo 의 `develop/UNIV-v1.0.0.0`. 새 워크스페이스에 합류하면 이 변형 가능성을 먼저 인지하고, 실제 머지 이력으로 컨벤션을 확정한 뒤 브랜치를 만든다.
>
> 아래 항목과 본 문서 이하의 `develop/...` 예시 표기는 모두 **해당 리포 컨벤션으로 대체**해서 읽는다.

- **개발 통합 브랜치**: 리포 컨벤션의 버전 자리에 버전. 예(decg-go): `decg-link/develop/v1.0.0.0`.
- **태스크 브랜치 (개발 모드)**: 통합 브랜치 컨벤션을 따르되 버전 자리에 Jira 키(소문자), 또는 리포가 쓰는 단기 브랜치 규칙. 정확한 형태는 해당 리포 이력을 따른다.
- **분석/문서 브랜치 (분석 모드)**: `analysis/<topic>` 또는 `docs/<topic>`
  - 예: `analysis/legacy-auth-audit`, `docs/architecture-current-state`
- 메인: `main` (배포 가능한 안정 상태만 머지).

### 2.2 생성 기준

- 개발 통합 브랜치는 **항상 `main` 에서 분기**한다. (예시는 decg-go 컨벤션 `<product>/develop/v<version>`. 다른 리포는 §2.1 의 해당 형태로 대체.)
  ```bash
  git checkout main && git pull
  git checkout -b decg-link/develop/v1.0.0.0
  git push -u origin decg-link/develop/v1.0.0.0
  ```
- 태스크 브랜치는 **항상 해당 프로젝트의 개발 통합 브랜치에서 분기**한다.
  ```bash
  git checkout decg-link/develop/v1.0.0.0 && git pull
  git checkout -b decg-link/develop/tecg-123
  ```
- 분석/문서 브랜치는 `main` 에서 분기한다 (산출물이 운영 코드와 무관).

### 2.3 머지 방향

- 태스크 브랜치 → **개발 통합 브랜치** (PR + 리뷰 통과 후).
- 개발 통합 브랜치 → **`main`** — 모든 태스크 완료 후 **별도 요청이 있을 때만** PR 생성.
- 분석/문서 브랜치 → **`main`** (분석 모드, 사용자 승인 후 직접 머지 가능. 운영 코드 변경 없음). **단, 사용자가 커밋·머지를 요청한 문서에 한함** — §5 산출물 커밋 금지 룰.
- `main` 으로 머지가 완료되면 **태그를 찍는다**(예: `v1.0.0.0`). 문서-only 머지는 태그 불필요.
- 핫픽스 외에는 `main` 으로의 직접 푸시·머지를 금지한다 (분석 모드 머지 제외).

### 2.4 작업 폴더 격리 (2026-10-04)

- 팀 설정 `@worktree` 에 적힌 멤버(개발·검증·디자인·에셋)는 **전용 git worktree**(`<저장소>-wt/<이름>`)에서 기동한다. 정체 블록의 "작업 폴더" 가 자기 위치다.
- **브랜치 전환·커밋·rebase 는 자기 worktree 에서만** 한다. 공유 작업 폴더(`$TEAM_WORKDIR`)에서는 브랜치를 바꾸지 않는다 — 다른 멤버의 화면과 인덱스가 같이 바뀐다.
- 새 worktree 는 detached HEAD 로 시작한다. 태스크 브랜치는 §2.2 대로 통합 브랜치에서 만든다(`git switch -c <태스크 브랜치> <통합 브랜치>`).
- **리뷰용 체크아웃**: 한 브랜치는 한 worktree 에서만 체크아웃된다. 검증자(정민·카맥 등)는 자기 worktree 에서 `git switch --detach <리뷰할 브랜치>` 로 본다 — 작성자의 worktree 에 들어가지 않는다.
- **커밋하지 않는 공유 산출물**(분석·명세·진단 문서, §5)은 공유 작업 폴더 `$TEAM_WORKDIR` 에 쓰고 `team-send` 로 **절대 경로**를 알린다. worktree 안의 미추적 파일은 다른 멤버에게 보이지 않는다.
- 미추적 로컬 설정(`.env`, 로컬 권한 파일 등)은 worktree 에 복사되지 않는다. 필요하면 제임스에게 보고하고 임의로 공유 폴더 파일을 옮기지 않는다.
- worktree 는 자동 삭제되지 않는다. 정리는 사용자 승인 후 `git worktree remove`.

## 3. 작업 흐름 (개발 모드, 태스크 단위)

1. **이슈 픽업** — Jira Sub-task 선택. 상태 `In Progress` 로 전환. **한 Sub-task 의 담당자는 1명** — 두 멤버가 같은 Sub-task·같은 파일을 동시 수정 중임을 발견하면 작업을 멈추고 즉시 제임스에게 `team-send` 로 보고해 담당을 정리한다 (예외: 명시적으로 합의된 협업만).
2. **브랜치 생성** — `develop/<product>/<jira-key>` 를 개발 통합 브랜치에서 분기. **자기 worktree 에서** 만든다(§2.4).
3. **개발** — 역할별 워크플로(TDD, 설계, 디자인 등) 를 따른다. 새 소스 파일 첫 줄에는 파일 역할을 설명하는 한 줄 한국어 헤더 주석을 둔다.
4. **로컬 검증** — 빌드·테스트·린트·타입체크 모두 통과.
5. **커밋** — Conventional Commits 형식. 메시지 본문에 Jira 키 포함.
   ```
   feat(auth): 세션 저장소 도입

   Refs: TECG-123
   ```
6. **PR 생성** — base 는 개발 통합 브랜치. 제목과 본문에 Jira 키 명시.
   - 제목 예: `[TECG-123] 세션 저장소 도입`
   - 본문에 Summary / Test plan / 관련 ADR·문서 링크.
7. **리뷰 파이프라인** — 7 절 "순환 검증" 참조. 정민·카맥·(필요 시) 네이선 단계 통과.
8. **머지** — Squash 또는 Merge commit(팀 합의). 머지 후 Jira 이슈 `Done` 으로 전환.
9. **브랜치 정리** — 태스크 브랜치는 머지 후 삭제.

### 3.10 버그 처리 흐름 (개발 모드) — SSOT

> 버그·동작 불량 보고의 표준 경로. 롤 파일(제임스 (b)·정민·마크)은 본 절을 참조한다.

1. **버그 보고 → 제임스 라우팅.** 제임스는 코드를 직접 확인하지 않고 정민 트리아지로 넘긴다.
2. **정민 트리아지** — 재현·심각도(CRITICAL/HIGH/MED/LOW, 모호 시 상향 default-up, 보안 의심은 CRITICAL 에스컬레이션)·영향 범위 정리.
   - 재현 성공 → Jira Sub-task 생성(재현 절차 필수 필드) → `team-send 마크 <키>`.
   - 재현 불가 → 타임박스 후 **조사 Sub-task**(수정 아님) 생성 → 마크가 finding-note(§6, `docs/analysis/findings/<topic>.md`)로 원인 규명. 조사 → 수정 재분류는 제임스가 상정하고 사용자가 결정(§0.3).
3. **(정민 "영향 큼" 판정 시) 네이선 영향 분석 선행** — 마크 착수 전. 산출물 `docs/analysis/impact/<feature>.md` (네이선 소유).
4. **마크 수정** — TDD(정민 재현 절차를 RED 재료로) → 브랜치·PR·§7.1 게이트.
5. **예외(운영 CRITICAL)** — 마크 즉시 착수 허용. 단 핫픽스 PR 머지 전까지 정민이 티켓 생성·링크(§2.3·§5 감사성).

## 4. 릴리스 (개발 통합 → main)

별도 요청이 있을 때만 진행한다.

1. 개발 통합 브랜치의 모든 Sub-task 가 `Done` 인지 확인.
2. 전체 회귀 테스트 통과 확인(정민 책임).
3. **성능 회귀** 통과 확인(카맥 책임 — `docs/performance/regression-perf.md` 의 임계값 충족).
4. `main` 으로의 PR 생성. 제목 예: `Release decg-link v1.0.0.0`.
5. 제임스가 검증 결과를 정리해 상정 → **사용자 최종 승인** 후 머지.
6. **태그 생성과 푸시**:
   ```bash
   git checkout main && git pull
   git tag -a v1.0.0.0 -m "Release decg-link v1.0.0.0"
   git push origin v1.0.0.0
   ```
7. Jira 상위(프로젝트) 이슈를 `Done` 으로 전환하고 릴리스 노트 링크.

## 5. 금지 사항

- `main` 으로 직접 푸시 / force-push (분석 모드 문서 머지 제외, 사용자 승인 필수).
- **개발 모드에서** Jira 이슈 없는 코드 변경.
- 리뷰 없이 개발 통합 브랜치로 머지.
- 보안·성능 회귀가 발견된 PR 의 강제 머지.
- `--no-verify`, `--force` 등 우회 옵션 사용(명시 요청 없을 시).
- 하나의 PR 에 여러 태스크 묶기.
- 분석 모드에서 운영 코드 직접 수정.
- 담당자 미합의 상태로 다른 멤버가 작업 중인 Sub-task·파일에 손대기 (충돌 발견 시 즉시 제임스 보고).
- **사용자 요청 없는 산출물 문서의 git 커밋 (CEO 룰 2026-06-10).** 멤버가 생성하는 산출물 문서(`docs/analysis/*`, `docs/performance/*`, `docs/qa/*`, 리뷰 로그·체크포인트·진단 메모 등)는 작업 트리에 생성·갱신하고 `team-send` 로 경로를 공유하되 **커밋하지 않는다**. 사용자가 명시적으로 커밋을 요청한 문서만 커밋에 포함한다. 코드 변경 PR 에 산출물 문서를 끼워 넣는 것도 금지.

## 6. 분석 모드 워크플로 (공통 가이드)

> 코드를 변경하지 않고 산출물(문서·표·다이어그램)만 만든다. 롤별 상세 단계는 각 롤 파일을 참조한다.
>
> **산출물 커밋 정책 (§5)**: 산출물은 파일로 생성하고 `team-send` 로 경로를 공유한다. git 커밋은 사용자가 요청한 문서만.
>
> **종합 분석 요청은 제임스 단독 작성 금지.** 제임스는 5명(네이선·정민·카맥·수영·수진) 에게 `team-send` 로 분담 위임 후 검수·통합만 수행. 단일 관점("보안만") 또는 단순 상태 조회("진행률만") 만 예외 — 두 예외 모두 사용자 발화에 명시적 한정 표현이 있을 때만 적용.

1. **스코프 선언** — 한 문장으로 적는다 (예: "결제 모듈의 보안·성능 audit").
2. **목적·이해관계자·종료 기준** 을 1 페이지로 정리.
3. **선행 자료 수집** — 기존 `docs/` 트리 + 코드베이스 인벤토리 (수진 담당).
4. **롤별 분석 수행** — 네이선(구조), 정민(보안·품질), 카맥(성능), 수영(UI/a11y), 수진(인벤토리·의존성). 제임스가 5명에게 `team-send` 로 동시 분담 위임. 기본 5명 유지하되, 구현 비중이 큰 audit 은 제임스가 마크를 6번째(구현 실행가능성 렌즈)로 on-demand 추가한다.
5. **산출물 통합** — 수진이 `docs/analysis/index.md` 에 등재. 제임스가 5종 검수(스코프/형식/누락/품질/정합) 통과 후 `docs/diagnostics/state-of-system.md` 에 종합.
6. **상정** — 제임스가 산출물 묶음을 검수·종합하고, 후속 액션(개발 모드 전환 포함) 채택을 결정 요청서로 사용자에게 상정한다.

## 7. 순환 검증 구조 (Cyclic Verification)

> 단일 게이트가 아닌 다단계 체크포인트와 주기적 루프로 품질을 지속적으로 유지한다.

### 7.1 Per-PR 검증 파이프라인 (개발 모드)

**일반 dev 브랜치 PR (대부분의 경우)** — 제임스 SKIP.

```
마크 (구현 + 자가 테스트, TDD + PR 라벨 자가부착)
   │
   ├──→ 정민 (코드 리뷰 + 보안 체크리스트 + 변경라인 커버리지)  ← CRITICAL/HIGH·커버리지 미달 시 마크 반려
   ├──→ 카맥 (perf budget + 회귀)                              ← perf budget 초과 시 마크 반려 (perf-waive 라벨 시 "perf 무관—통과" fast-pass)
   └──→ 네이선 (아키텍처 정합성)                                ← interface-change 라벨 PR 만. 인터페이스 정의 대조·ADR 위배 시 마크 반려
        (정민·카맥·네이선 동시 병렬 검토 — 직렬 금지)
   ↓
[해당 게이트 모두 통과 (네이선은 interface-change PR 에서만)]
   ↓
**dev 브랜치 머지 — 제임스 사전 승인 불요**
```

**PR 라벨 (마크 자가부착 · §7.1 게이트 분기 기준 — 조건부 게이트 고아 방지 단일 정의)**

- `interface-change` — 공개/모듈 경계 시그니처(export 타입·함수), API 스키마, 이벤트 계약, DB 스키마 변경 PR 에 부착. 내부 구현·리팩터는 비대상. 부착 시 네이선 아키텍처 정합성 리뷰가 정민·카맥과 **병렬** 발동. 정민이 영향 범위 분석 중 오라벨(미부착·과부착) 을 백스톱으로 교정.
- `perf-waive` — 런타임 표면이 없는 PR(docs·test-only·config) 에 부착. 부착 시 카맥이 "perf 무관—통과" fast-pass. 미부착 PR 은 카맥 perf 게이트 필수.
- **커버리지**: 정민 게이트는 변경 라인(patch) 커버리지 80% 미달 시 마크 반려. patch coverage 도구 부재 시 정민이 신규·변경 함수의 대응 테스트 존재를 리뷰로 확인 (도구 도입은 별도 티켓).

**main 머지 PR (릴리스 시점만)** — 여기서만 제임스 진입.

```
dev 브랜치 (모든 Sub-task 완료) → 제임스 (릴리스 상정) → 사용자 승인 → main 머지 + 태그
```

- 각 단계는 **명시적 통과·반려** 코멘트를 남긴다.
- 반려된 PR 은 사유와 함께 1단계 (마크) 로 돌아간다.
- 정민·카맥 (+ interface-change PR 은 네이선) 은 동시 병렬 검토 (해당 게이트 모두 통과해야 dev 머지).
- **제임스는 일반 dev PR 에 끼어들지 않는다.** 코드 리뷰·perf 검증은 정민·카맥이 자율 수행. 제임스 진입 시점은 (a) dev → main 릴리스 상정, (b) 정민·카맥 사이에서 조정이 필요한 충돌 발생, (c) CRITICAL 보안 이슈 보고 — 세 가지뿐.
- **마크는 PR 완료 시 정민·카맥 (+ interface-change PR 은 네이선) 에게 병렬 `team-send` 송신**한다. 원 발신자(제임스 등) 에게는 해당 게이트 모두 통과 후 "상태 보고" 만 전달 (승인 요청이 아님).

> 현재 리포에 Jira 자동 생성 훅·CI 는 없다 (검증 2026-07-09: settings.json 훅 = rtk·team-send-verify 만, CI 부재). 아래는 발견자가 `team-send` 로 요청하는 수동 트리거이며, Jira 생성은 MCP `jira_create_issue` 를 담당자가 직접 호출한다.

## 8. 페인 간 메시지 전달 (Pane-to-Pane Messaging)

> 팀원 간 위임·질의·회신은 **`team-send` 헬퍼**를 통한 tmux 페인 주입으로 표준화한다. 사용자가 메시지를 수동 중계할 필요가 없다.

### 8.1 멤버 구성 (2026-10-02)

| 창 | 파트 | 멤버 (엔진) |
|---|---|---|
| 기획 | 진행 | 제임스 (Claude) |
| 기획 | 교육 리서치 페어 | 비고츠키 (Claude) · 블룸 (Codex) |
| 기획 | 콘텐츠 기획 페어 | 파인만 (Claude) · 세이건 (Codex) |
| 기획 | 게임 기획 페어 | 미야모토 (Claude) · 라이트 (Codex) |
| 개발 | 아키텍처 · 백엔드 · 클라이언트 | 네이선 · 마크 · 이와타 (Claude) |
| 개발 | 검증 게이트 | 정민 (QA·보안) · 카맥 (성능) (Codex) |
| 개발 | 리서치 · 디자인 · 에셋 | 수진 · 수영 · 히사이시 (Claude) |

> 위 표는 학습 게임 팀(`teams/edu-game.conf`)이다. 아이디어 팀(`teams/idea.conf`)은 §14 참조. 내러티브 게임 팀(`teams/narrative.conf`)은 교육 리서치·콘텐츠 기획 페어 대신 **디렉터 우에다(Claude)** 와 **시나리오 기획 페어 닥터(Claude)·드럭만(Codex)** 이 기획 창에 들어간다.
>
> **이 팀에 없는 멤버** — 역할 파일·이 문서는 여러 팀 공용이라 다른 팀의 멤버(예: 아이디어 팀의 정민·카맥, 내러티브 팀의 파인만·세이건)를 부를 수 있다. 정체 블록의 **팀 명단**에 없으면 같은 블록의 **대체 담당 표**(팀 설정 `@substitute`)를 따르고, 표에도 없으면 제임스에게 보낸다. 부재 멤버에게 `team-send` 를 시도하지 않는다(알 수 없는 수신자로 실패).
> **프로젝트별 책임** — 정체 블록의 "이 프로젝트에서의 책임"(팀 설정 `@duty`)은 역할 파일의 책임 범위보다 우선한다.
>
> 구성의 SSOT 는 팀 설정 파일(`teams/*.conf`)이고 `setup-team.sh`·`team-send` 가 같은 파일을 읽는다. 실제 이름·별칭·멤버 번호는 `team-send -h`, 상태는 `team-status` 로 확인한다. 창이 달라도 **이름으로** `team-send` 를 호출하면 된다. 페인 번호를 직접 쓰지 않는다.

### 8.2 송신 (team-send 헬퍼)

**중요 — 호출 방식**: `team-send` 는 **반드시 Bash 도구로 실행한다**.
- ✅ 올바른 호출: `Bash("team-send 마크 'ADR-014 1단계 부탁'")`
- ❌ **금지: sub-agent spawn 호출** (Claude `Task(subagent_type="마크", ...)`, Codex 하위 에이전트 등). 팀원은 sub-agent 가 아니라 **별도 tmux 페인의 독립 Claude/Codex 인스턴스**다. sub-agent 도구는 팀원을 찾을 수 없다.
- ❌ **금지: 메시지 구성 ≠ 실행.** `team-send ...` 를 자연어 응답으로 출력만 하기, input prompt 에 입력만 하고 Enter 없이 종료하기, "X 에게 송신해줘" 자가 노트로 적어 두기 — 전부 실행이 아니다. 반드시 Bash 도구 호출 + `✅ ... (pane N)` 종료 코드 0 확인.

```bash
# 한 줄 메시지
team-send 마크 "ADR-014 의 1단계(SessionStore + 미들웨어 교체) 부탁합니다. 기한 5/19."

# 파일에서 읽기 (긴 위임 지시서·산출물)
team-send 네이선 -f docs/decisions/2026-05-14-multi-pg.md

# stdin 으로 파이프
cat report.md | team-send 제임스
```

헬퍼는 자동으로:
- 발신자(현재 페인) 를 식별하여 `[From: 제임스 → 마크] 2026-05-14 10:15` 헤더 부착
- bracketed paste 로 멀티라인 메시지를 한 청크로 안전하게 전달
- 마지막에 Enter 를 눌러 수신자(Claude/Codex)가 즉시 처리하도록 하고, 입력창 잔존을 확인해 필요하면 Enter 를 재발사
- 수신자 페인이 비활성(CLI 종료) 이면 exit 4 로 거절
- 수신자가 Codex 이고 5시간 한도가 30% 미만이면 경고 출력 (§0.5.1)

`--no-header` 로 헤더 생략, `--session <name>` 으로 비기본 세션 지정 가능. 세션은 `--session` → `TEAM_SESSION`(멤버 페인 자동 지정) → 호출 페인의 세션 순으로 정하므로 여러 팀을 동시에 띄워도 자기 팀으로 간다. tmux 밖에서 세션이 여럿이면 `--session` 이 필수다.

### 8.2.1 송신 후 검증 (의무 — 모든 크기 메시지 공통)

`team-send` 호출 후 **반드시 다음 4단계 확인**한 뒤에야 "전달 완료" 보고. 검증 없는 "전달 완료" 보고 금지 — LLM 환각으로 거짓 보고가 발생한다.

1. Bash 도구의 **종료 코드 = 0** (셸 출력 마지막 줄 `✅ <발신> → <수신> (pane N)`)
2. 비0 종료 시 stderr 메시지로 원인 식별 (exit 3 = 세션·페인 없음, exit 4 = 비활성, exit 5 = 전달 미확인 — 같은 메시지를 재전송하지 말고 3단계로 확인 후 제임스에게 보고)
3. **수신자 페인 capture 으로 메시지 전달 확인** — `team-status --tail 15` 로 수신자 미리보기 확인 (페인 번호는 tmux 설정에 따라 달라지므로 직접 지정하지 않는다)
4. **Enter 발동 확인** — 수신자 화면에 작업 표시가 있어야 active. Claude: spinner (`✻ Thinking…` 등)·`esc to interrupt` / Codex: `Working (… esc to interrupt)` 또는 대기열 `Messages to be submitted`. 입력창(Claude `❯`, Codex `›`)에 메시지 잔존이면 Enter 미발동 — `team-send` 가 자동 재발사하며, 그래도 남아 있거나 입력창을 찾지 못하면 `delivery 미확인` + exit 5 로 끝난다 — 제임스에게 보고

**자동화** — `team-send` 자체가 4단계(입력창 잔존 확인·Enter 재발사)를 수행한다. Claude 멤버는 추가로 `team-send-verify` PostToolUse Hook 이 전송 이력을 기록한다(Codex 에는 이 Hook 이 없다). 로그 `/tmp/team-send-verify.log`, 가이드 `~/.claude/skills/team-send-verify/SKILL.md`. **Hook 는 보완책이지 면제책 아님** — Hook 실패 (jq 미설치·tmux 비가용·스크립트 손상) 시 위 4단계를 매뉴얼 수행한다.

### 8.3 수신 규약

각 멤버는 자기 페인에 도착한 메시지의 **첫 줄**을 검사한다.

- `[From: <발신자> → <본인>] <시각>` 형식이면 **위임/질의** 로 인식하고 작업을 시작한다.
- 헤더가 없으면 사용자 직접 입력으로 간주한다.

### 8.4 회신 (의무, 화면 출력 ≠ 송신)

**핵심 원칙** — 응답을 본인 페인 화면에 출력하거나 input prompt 에 적어 두는 것은 송신이 아니다. 반드시 `team-send` 명령(Bash 도구)으로 발신자 페인에 실제 송신해야 도착한다. 위반 시 발신자는 결과를 영원히 모른다.

**의무 — 다음 시점에 반드시 `team-send` 회신**:

1. 위임받은 작업 단계 완료 시 — 결과·다음 단계·블로커 보고
2. 위임받은 작업 중 결정 필요 시 — 승인 요청 (자기 페인에만 적고 idle 진입 금지)
3. 위임받은 작업 중 에러·차단 발생 시 — 즉시 진단 보고
4. 멤버 간 협업이 필요할 때 — 자가 노트가 아니라 `team-send <대상>` 명령으로 실제 송신
5. 외부 영향 큰 단계 (commit/push/머지/외부 송신) 도착 시 — 사용자 확인 대기로 idle 금지. 위임 지시서 범위 내 자율 진행 + 결과 회신

```bash
team-send 제임스 "[결과] TECG-123 1단계 완료. PR #142, 리뷰 요청 송신함."
team-send 카맥 "[질의] perf 회귀 1.5x 의심 — 베이스라인 재측정 협조 부탁드립니다."
```

**응답 종료 전 자가 점검** — 하나라도 누락 시 응답 종료 금지, team-send 송신 후 종료한다:

1. 위임받은 발신자에게 진행 단계·결과·블로커를 `team-send` 으로 송신했는가?
2. 협업 대상 멤버에게 실제 송신했는가? (input prompt 자가 노트 금지)
3. 송신 결과 `✅ <발신> → <수신> (pane N)` + 종료 코드 0 을 확인했는가?

### 8.4.1 "영역" 단어 placeholder 금지 (절대 규칙)

한국어 응답에서 **"영역" 단어를 placeholder처럼 반복 사용 금지**. LLM 토큰 생성 폴백 패턴으로 가독성을 심각하게 해친다.

**금지 예시** (실제 발생 사례):
- ❌ "Linux 영역 영역 영역 영역 영역" → ✅ "Linux 운영 측면 / Linux 환경 / Linux 동작"
- ❌ "사고 영역 영역" → ✅ "사고 처리 / 사고 사례 / 사고 시점"
- ❌ "본인 영역 영역" → ✅ "본인 입장 / 본인 판단 / 본인 권장"
- ❌ "머지 영역 영역" → ✅ "머지 시점 / 머지 결과 / 머지 처리"

**적용 의무**:
1. 응답 작성 중 "영역" 단어 사용 시 즉시 구체적 명사로 대체 (부분 / 점 / 항목 / 단계 / 상태 / 시점 / 내용 / 사유 / 결과 / 측면 / 사항 / 분류 / 요인 / 경우 / 때 / 곳 / 시 / 후 / 전 / 측 / 쪽)
2. **응답 송신 직전 의무 점검**: 본문 전체에서 "영역" 단어 grep → 1개라도 발견되면 송신 금지, 정정 후 송신
3. 적절한 명사를 찾지 못하면 문장 자체 재구성 또는 해당 부분 삭제

**Why**: 2026-05-27 CEO 첫 지적 → 2026-06-09 재지적 (강도 강화: "널 지워버리기 전에"). 본 표준 등재 후에도 반복 위반 발생. placeholder 반복은 LLM 출력 결함 신호이며 CEO 책망의 직접 원인.

**Quoted reference 예외 (2026-06-09 네이선 자가 식별 + CEO 결재)**:
- ✅ 허용: 표준 문서 본문 (본 §8.4.1 자기 정의), 자가 점검 grep 명령, 표준 위반 인용 보고 (정민 review-log, 사고 보고 등)
- ❌ 금지: 일반 응답 본문 (모든 멤버 회신, 사용자 답변)
- 대체 표기: `Y-단어` / `placeholder 단어` / `금지 단어` / `해당 단어` 사용
- 메타 토론 (표준 정의 / 자가 점검 / 위반 보고) 외 모든 본문에서 placeholder 자체 표기 회피

### 8.5 브로드캐스트·다중 전달

`team-send` 는 1:1 만 지원. 1:N 이 필요하면 반복 호출.

```bash
for who in 네이선 마크 카맥; do
    team-send "$who" -f docs/decisions/2026-05-14-multi-pg.md
done
```

### 8.6 운영 주의사항

- 메시지는 수신자의 **다음 프롬프트로 그대로 주입**되므로, 대화 중일 때는 약간의 컨텍스트 단절이 생길 수 있다. 위임 전 수신자 페인이 응답 대기 중인지 확인 권장.
- 인용 코드 블록, 백틱, 큰따옴표는 헬퍼가 bracketed paste 로 처리하므로 이스케이프 불필요.
- 매우 긴 메시지(> 8KB) 는 파일로 보내고 경로만 전달하는 패턴 권장 (`team-send 마크 "docs/guides/auth.md 참조"`).

### 8.7 사용자에게 메시지 전달을 부탁하지 않는다 (절대 규칙)

**팀 자동화의 핵심 원칙**: 사용자는 결정·승인 요청 대상이지, 메시지 중계자가 아니다.

`team-send` 가 실패해도 다음 순서로 자력 해결한다.

1. **명령어 재확인** — 수신자 이름·따옴표·파일 경로 오타 점검.
2. **수신자 페인 상태 진단**:
   ```bash
   team-status --tail 10
   ```
   - `[INACT]` 는 CLI 가 종료되고 셸만 남은 비활성 페인. team-send 가 exit 4 로 거절함.
   - `[OK]` 는 정상 활성 (Claude 는 버전 번호, Codex 는 `node` 로 표시).
3. **재시도** — 일시적 응답 지연이면 잠시 후 재발송.
4. **그래도 해결 불가능 한 경우** — 사용자에게 보고하되 **다음 형식**으로만:
   - ✅ 허용: `[시스템 장애] <대상> 페인 비활성. 재시작 결정 요청드립니다.`
   - ❌ 금지: `사용자님이 대신 team-send 실행해 주세요`, `직접 전달 부탁드립니다`, `터미널에서 아래 명령 실행 부탁`

**근거**: 사용자에게 전달 대행을 요청하는 순간 자동화가 깨진다. 사용자가 손으로 옮긴 메시지는 발신자 추적·타임스탬프·정합성이 모두 끊긴다.

- **마크 (Developer)** — 브랜치 생성, 커밋, PR, Jira 상태 전환 / **단위·통합 테스트는 마크가 작성 (TDD 원칙)** / 분석 모드에서 finding note.

- **수진 (Researcher)** — 리서치도 Sub-task 로 등록. 결과 문서는 team-send 로 경로 공유 (커밋은 §5 우선 — 사용자 요청 시에만 PR) / 코드 인벤토리·의존성 감사 월간 갱신.

- **카맥 (Performance Engineer)** — 성능 베이스라인·perf budget 유지 / per-PR perf 게이트 / 부하 테스트 / 관측성 가이드 / 주간 perf 회귀 점검.

## 10. 기획 파트 — 결정 페어 프로토콜 (2026-10-02)

> 교육 리서치·콘텐츠 기획·게임 기획은 **Claude 1명 + Codex 1명** 페어로 운영한다. 목적은 서로 다른 모델의 독립된 안을 비교해 사용자가 최선의 선택을 하도록 돕는 것이다. 페어는 결정하지 않는다.

### 10.1 진행 순서

1. **쟁점 정의 (제임스)** — 결정 ID `D-YYYYMMDD-N`, 질문 한 줄, 제약, 평가 기준, 기한을 정해 **페어 양쪽에 같은 내용으로 동시에** 송신한다. 송신 전 `team-status --limits` 로 Codex 한도를 확인한다(§0.5.1).
2. **독립 초안 (페어 각자)** — `docs/decisions/pending/<결정ID>/<본인이름>.md` 에 작성한다. 이 단계에서는 **상대 초안을 읽지 않는다**(앵커링 방지). 완료 시 제임스에게 경로만 보고한다.
3. **교환 (제임스)** — 두 초안이 모두 도착하면 양쪽에 서로의 경로를 보낸다.
4. **상호 비판 (최대 2라운드)** — 각자 `<본인이름>-review-<n>.md` 에 상대 안에 대해 동의·반대·근거·수정 제안을 적고 상대와 제임스에게 경로를 보낸다. 새 근거 없는 반복 주장 금지. 2라운드 후에도 남은 이견은 **억지로 합의하지 않고 쟁점으로 남긴다.**
5. **결정 요청서 (페어)** — Claude 측이 초안을 쓰고 Codex 측이 검토해 서명한다. 서명은 "내 입장이 정확히 반영됐다" 는 확인이지 동의가 아니다. 경로: `docs/decisions/pending/<결정ID>/request.md`.
6. **상정 (제임스)** — 다른 파트 영향이 있으면 해당 멤버(예: 구현 비용 → 네이선·이와타, 학습 효과 측정 → 비고츠키·블룸)에게 1회 의견을 받아 덧붙인다. 제임스 본인의 의견은 "진행자 가이드" 로 **분리 표기**하고 사용자에게 상정한다.
7. **결정·기록 (사용자 → 제임스)** — 사용자 결정을 `docs/decisions/YYYY-MM-DD-<slug>.md` 에 기록(결정자: 사용자)하고 관련 멤버에게 전파한다. 개발로 넘길 내용은 §12 로 인계한다.

### 10.2 페어 운영 규칙

- 페어 두 사람은 같은 역할 파일을 쓰지만 **관점이 다르다**(역할 파일의 "페어 구성"). 상대 관점에 맞춰 자기 관점을 지우지 않는다.
- 상대가 다른 모델이라는 이유로 신뢰하거나 불신하지 않는다. 근거로만 판단한다(품질 원칙 2).
- 한쪽 페인이 비활성이거나 Codex 한도가 부족하면 진행을 멈추고 제임스에게 보고한다. 한쪽 안만으로 결정 요청서를 만들지 않는다.

### 10.3 결정 요청서 형식

```markdown
# 결정 요청: <질문 한 줄>
- 결정 ID / 기한 / 작성: <Claude 측> · 검토 서명: <Codex 측> · 진행: 제임스
## 배경과 평가 기준
## 합의된 사항
## 쟁점 (입장별 근거)
| 쟁점 | <Claude 측> 입장·근거 | <Codex 측> 입장·근거 |
## 선택지
| 선택지 | 장점 | 단점·리스크 | 비용·일정 | 되돌리기 쉬움 |
## 페어 권장 (이견 시 각자)
## 진행자 가이드 (제임스 — 결정 아님)
## 결정 후 후속 작업
```

## 11. 개발 파트 — 교차 검증 (2026-10-02)

- **만드는 쪽은 Claude, 검증하는 쪽은 Codex.** 네이선·마크·이와타·수영·히사이시·수진의 산출물은 정민(품질·보안)·카맥(성능)이 검증한다. 같은 모델끼리 같은 실수를 놓치는 위험을 줄이기 위함이다(엔진 배정은 팀 설정 `teams/*.conf` 가 SSOT).
- **코드** — §7.1 PR 게이트를 그대로 적용한다. 이와타의 클라이언트 PR 도 동일.
- **ADR·기술 선택** — 네이선 초안 → 정민·카맥이 반론 담당(약점·대안·숨은 비용을 찾는 역할)으로 검토 → 네이선이 반영·미반영 사유 기록 → 제임스가 결정 요청서(§10.3 형식)로 상정 → 사용자 결정.
- 검증자는 작성자의 경력·직책·모델을 근거로 통과시키지 않는다. 통과/반려를 근거와 함께 명시한다.

## 12. 기획 → 개발 인계 (2026-10-02)

| 사용자가 채택한 기획 | 받는 멤버 | 산출 |
|---|---|---|
| 학습 목표·평가 설계 (교육 리서치) | 네이선 · 마크 · 카맥 | 학습 이벤트·지표 데이터 모델, 수집·분석 경로 |
| 콘텐츠 명세·데이터 구조 (콘텐츠 기획) | 네이선 · 마크 | 콘텐츠 스키마·검수 파이프라인 ADR |
| 게임 기획서·밸런스 표 (게임 기획) | 네이선 · 이와타 · 수영 | 구현 가이드, 화면·상호작용 설계 |
| 아트·사운드 방향 (게임 기획 · 수영) | 히사이시 | 에셋 명세·도구 조사·조달 계획 |

- 인계는 제임스가 결정 기록 경로와 함께 `team-send` 로 지시한다. 받는 멤버는 기획 의도가 불명확하면 해당 페어에게 직접 질의한다.
- 개발 중 기획 변경이 필요하면 임의로 바꾸지 않고 제임스에게 보고한다 → 해당 페어 검토 → 사용자 결정.

## 13. 디렉터 위임 (내러티브 팀, 2026-10-02)

> 사용자가 디렉터 우에다에게 **작은 창작 판단**을 위임했다. 큰 창작 결정은 여전히 사용자 몫이다. 상세 범위는 `roles/우에다.md` "위임된 판단 범위".

| 위임됨 (우에다 판단·기록) | 위임 안 됨 (사용자 결정) |
|---|---|
| 대사 문구 다듬기(뜻·사건·관계 불변), 장면 안 연출 세부(카메라·컷 길이·침묵·전환), 음악 큐 위치, 같은 의도 안의 표현 선택, 플레이테스트 감정 관찰 항목 | 줄거리·결말·인물의 생사와 관계 변화, 장 구성·분기 구조·결말 수, 톤 바이블 변경, 외부 도구·예산·일정, 페어 간 남은 이견 |

- 위임 판단은 모두 `docs/direction/delegated-log.md` 에 기록한다. 사용자는 언제든 뒤집을 수 있다.
- 애매하면 위임 밖으로 본다. 위임 판단이 누적돼 큰 결정이 되는 조짐이 보이면 결정 요청서로 전환한다.
- 다른 멤버는 위임 범위 안의 우에다 판단을 따르되, 근거 있는 이견은 우에다에게 제기하고 해소되지 않으면 제임스에게 보고한다(사용자 상정).
- 시나리오·게임 기획 페어의 결정 요청서에는 우에다의 연출·톤 의견을 1회 덧붙인다(§10.1 6단계).

## 14. 아이디어 팀 — 컨셉에서 프로젝트 팀까지 (2026-10-02)

> 새 프로젝트는 아이디어 팀(`teams/idea.conf`, Claude 5 : Codex 5)에서 시작한다. 아이디어 팀은 **무엇을 만들지와 어떤 팀으로 만들지**를 사용자가 결정할 수 있게 준비한다. 구현은 하지 않는다.

### 14.1 구성과 관점

| 관점 | 멤버 (Claude · Codex) | 아이디어 단계에서 하는 일 |
|---|---|---|
| 진행 | 제임스 | 주제 정의, 발산·수렴 진행, 결정 요청서 상정, 팀 구성안 작성 |
| 컨셉 (결정 페어) | 미야모토 · 라이트 | 핵심 재미·코어 루프·플레이 경험 컨셉, 컨셉 결정 요청서 |
| 교육 | 비고츠키 · 블룸 | 학습 가치·대상 연령·학습 효과 가능성 |
| 서사 | 닥터 · 드럭만 | 이야기·감정·주인공 경험의 가능성 |
| 조사 | 수진 (Codex) | 시장·경쟁작·플랫폼 정책·기술 실현성 (웹 검색, 출처·확인일) |
| 규모 | 네이선 (Codex) | 컨셉별 구현 규모·기술 난이도·필요 역할 추정 |
| 비주얼 | 수영 | 분위기 키워드·참고 방향 (작품명이 아닌 느낌으로) |

각 멤버는 역할 파일의 범용 책임을 아이디어 단계에 맞게 적용한다 — 상세 명세·대본·코드가 아니라 **판단에 필요한 만큼의 컨셉 수준 산출물**만 만든다(§0.6).

### 14.2 진행 순서

1. **주제 정의 (제임스)** — 사용자의 아이디어·관심사를 주제 한 줄과 제약(기간·플랫폼·대상·예산)으로 정리. Codex 5명이 참여하므로 `team-status --limits` 확인.
2. **발산 (전원, 독립)** — 컨셉 2~3개씩을 `docs/concepts/<주제>/ideas/<본인이름>.md` 에 작성. 다른 멤버의 안을 읽지 않는다. 컨셉 형식: 한 줄 요약 / 플레이어 경험 / 핵심 재미 / 교육 가치 또는 감정 가치 / 참고 방향 / 우려.
3. **검증** — 제임스가 모은 후보(중복 병합, 최대 6개)를 각 관점이 평가한다: 수진(시장·경쟁작·실현성), 네이선(규모·난이도·필요 역할), 비고츠키·블룸(학습 가치), 닥터·드럭만(서사·감정 가치), 수영(비주얼 방향). 평가표 `docs/concepts/<주제>/evaluation.md`.
4. **컨셉 결정 요청 (미야모토·라이트)** — §10 페어 절차로 후보 2~3개를 비교한 결정 요청서. 각 후보에 **추천 프로젝트 유형**(학습 / 내러티브 / 혼합 / 기타)을 단다. → **사용자가 컨셉과 프로젝트 유형을 결정**.
5. **팀 구성안 (제임스)** — 가장 가까운 팀 설정(`edu-game`·`narrative` 등)을 출발점으로 `teams/<프로젝트>.conf` 초안을 만든다. 포함·제외 멤버와 이유, 엔진·effort, Claude : Codex 비율, 예상 Codex 사용량, 새 역할이 필요하면 그 역할의 요구 역량. → **사용자가 팀 구성을 결정**.
6. **인계** — 결정된 컨셉 문서 묶음(`docs/concepts/<주제>/`)을 프로젝트 폴더로 넘길 목록과, 프로젝트 팀 실행 명령(`setup-team <세션> -d <폴더> -c <프로젝트>`)을 사용자에게 보고한다. 아이디어 팀은 다음 주제로 넘어가거나 종료한다.

### 14.3 규칙

- 아이디어 팀은 구현·상세 명세·대량 대본을 만들지 않는다. 판단에 필요한 수준까지만.
- 팀 설정 파일(`teams/*.conf`)의 추가·수정은 사용자 결정 후에만 한다.
- 교육·서사 관점이 모두 맞지 않는 컨셉이면 그 사실을 명시하고, 필요한 다른 관점(예: 퍼즐·경쟁·협동)을 팀 구성안에서 제안한다.
