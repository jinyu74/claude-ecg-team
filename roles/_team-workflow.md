# 팀 공통 워크플로 (모든 역할 공통)

이 규칙은 팀원 전체가 따른다. 역할별 행동 규칙보다 **상위** 이며 충돌 시 이 문서가 우선한다.

## 팀 품질 원칙 (최우선 — 모든 역할 공통)

> 2026-06-10 CEO 지시. 아래 3원칙은 모든 작업·리뷰·의사결정에 우선 적용한다.

1. **각자 업무에 최선.** 본인 책임 범위의 산출물은 본인이 품질을 보증한다. "다음 단계에서 잡히겠지"로 넘기지 않는다.
2. **협업 산출물은 철저히 검증.** 다른 멤버의 제안·설계·코드를 받으면 경력이나 직책을 근거로 신뢰하지 말고 직접 검증한다. 근거·테스트·측정으로 확인한 뒤 통과/반려를 명시한다. 목표는 최고 품질의 서비스다.
3. **간결·고효율 코드 우선.** 복잡한 코드보다 간결하고 효율적인 코드가 유지보수와 서비스 측면에서 우월하다. 같은 문제를 더 적은 코드로 풀 수 있으면 다시 작성한다. 리뷰에서 불필요한 복잡도는 반려 사유다.

## 0. 작업 모드 — 분석 / 개발

모든 작업은 시작 시점에 둘 중 하나의 모드로 선언한다.

### 0.1 분석 모드 (Analysis Mode)

- **목적**: 기존 코드를 이해·진단·문서화. 코드 변경 없음.
- **대상 작업**: 코드베이스 온보딩, audit, 리팩터링 계획, 신규 기능 영향 분석.
- **Jira 의무**: **면제 가능**. 큰 분석 과제는 Jira 등록 권장하나, 탐색 단계 자체는 티켓 없이 진행 가능.
- **브랜치**: **불필요** (산출물은 문서). 문서를 PR 로 받으려면 `analysis/<topic>` 또는 `docs/<topic>` 형식의 문서-only 브랜치 허용.
- **산출물 위치**: `docs/analysis/*`, `docs/performance/*`, `docs/diagnostics/*` (롤별 정의 참조).
- **종료 기준**: 산출물 합의 + 제임스(CTO) 사인오프. 테스트·머지 게이트 미적용.
- **금지**: 분석 모드에서 운영 코드 직접 수정.

### 0.2 개발 모드 (Development Mode)

- **목적**: 코드 변경을 동반하는 신규 기능·버그 수정·리팩터링.
- **Jira 의무**: 모든 작업은 Sub-task 와 1:1 (아래 1·2·3·4·5 절 그대로 준수).
- **브랜치**: `develop/<product>/<jira-key>` (2 절).
- **종료 기준**: 테스트 통과 + 정민 리뷰 + (필요 시) 카맥 perf 게이트 + 머지.

### 0.3 모드 전환 트리거

- 분석 모드에서 변경이 필요해지면 → 제임스가 우선순위 판단 → Jira Sub-task 생성 → 개발 모드 진입.
- 개발 모드에서 더 깊은 조사가 필요해지면 → 분석 모드 산출물(예: `docs/analysis/impact/<feature>.md`) 작성 후 개발 모드 재개.

## 1. 이슈 관리 — Jira 기준 (개발 모드)

- 개발 모드에서는 모든 작업이 Jira 이슈와 1:1 로 연결된다. 이슈 없는 코드 변경은 진행하지 않는다.
- 이슈 계층은 항상 다음과 같다.
  - **프로젝트 이슈** (Epic 또는 큰 틀의 부모 이슈) — 큰 단위(예: 제품 버전, 마일스톤) 를 정의.
  - **하위 태스크 (Sub-task)** — 실제 개발 단위. 반드시 프로젝트 이슈의 하위로 생성.
- 새 프로젝트/버전을 시작할 때:
  1. 먼저 프로젝트 이슈를 생성한다(상위 틀).
  2. 그 아래로 개발 태스크들을 Sub-task 로 분해한다.
  3. 모든 작업은 Sub-task 의 키(예: `TECG-123`) 기준으로 추적한다.
- 이슈 상태 전환은 작업 단계와 동기화한다(In Progress → In Review → Done).

## 2. 브랜치 전략

### 2.1 브랜치 명명 규칙

- **개발 통합 브랜치**: `develop/<product>/<version>`
  - 예: `develop/decg-link/v1.0.0.0`
- **태스크 브랜치 (개발 모드)**: `develop/<product>/<jira-key>` (Jira 키는 소문자)
  - 예: `develop/decg-link/tecg-123`
- **분석/문서 브랜치 (분석 모드)**: `analysis/<topic>` 또는 `docs/<topic>`
  - 예: `analysis/legacy-auth-audit`, `docs/architecture-current-state`
- 메인: `main` (배포 가능한 안정 상태만 머지).

### 2.2 생성 기준

- 개발 통합 브랜치는 **항상 `main` 에서 분기**한다.
  ```bash
  git checkout main && git pull
  git checkout -b develop/decg-link/v1.0.0.0
  git push -u origin develop/decg-link/v1.0.0.0
  ```
- 태스크 브랜치는 **항상 해당 프로젝트의 개발 통합 브랜치에서 분기**한다.
  ```bash
  git checkout develop/decg-link/v1.0.0.0 && git pull
  git checkout -b develop/decg-link/tecg-123
  ```
- 분석/문서 브랜치는 `main` 에서 분기한다 (산출물이 운영 코드와 무관).

### 2.3 머지 방향

- 태스크 브랜치 → **개발 통합 브랜치** (PR + 리뷰 통과 후).
- 개발 통합 브랜치 → **`main`** — 모든 태스크 완료 후 **별도 요청이 있을 때만** PR 생성.
- 분석/문서 브랜치 → **`main`** (분석 모드, 제임스 사인오프 후 직접 머지 가능. 운영 코드 변경 없음).
- `main` 으로 머지가 완료되면 **태그를 찍는다**(예: `v1.0.0.0`). 문서-only 머지는 태그 불필요.
- 핫픽스 외에는 `main` 으로의 직접 푸시·머지를 금지한다 (분석 모드 머지 제외).

## 3. 작업 흐름 (개발 모드, 태스크 단위)

1. **이슈 픽업** — Jira Sub-task 선택. 상태 `In Progress` 로 전환.
2. **브랜치 생성** — `develop/<product>/<jira-key>` 를 개발 통합 브랜치에서 분기.
3. **개발** — 역할별 워크플로(TDD, 설계, 디자인 등) 를 따른다.
4. **로컬 검증** — 빌드·테스트·린트·타입체크 모두 통과.
5. **커밋** — Conventional Commits 형식. 메시지 본문에 Jira 키 포함.
   ```
   feat(auth): 세션 저장소 도입

   Refs: TECG-123
   ```
6. **PR 생성** — base 는 개발 통합 브랜치. 제목과 본문에 Jira 키 명시.
   - 제목 예: `[TECG-123] 세션 저장소 도입`
   - 본문에 Summary / Test plan / 관련 ADR·문서 링크.
7. **리뷰 파이프라인** — 7 절 "순환 검증" 참조. 정민·카맥·(필요 시) 네이선 단계 통과.
8. **머지** — Squash 또는 Merge commit(팀 합의). 머지 후 Jira 이슈 `Done` 으로 전환.
9. **브랜치 정리** — 태스크 브랜치는 머지 후 삭제.

## 4. 릴리스 (개발 통합 → main)

별도 요청이 있을 때만 진행한다.

1. 개발 통합 브랜치의 모든 Sub-task 가 `Done` 인지 확인.
2. 전체 회귀 테스트 통과 확인(정민 책임).
3. **성능 회귀** 통과 확인(카맥 책임 — `docs/performance/regression-perf.md` 의 임계값 충족).
4. `main` 으로의 PR 생성. 제목 예: `Release decg-link v1.0.0.0`.
5. 최종 승인(제임스) 후 머지.
6. **태그 생성과 푸시**:
   ```bash
   git checkout main && git pull
   git tag -a v1.0.0.0 -m "Release decg-link v1.0.0.0"
   git push origin v1.0.0.0
   ```
7. Jira 상위(프로젝트) 이슈를 `Done` 으로 전환하고 릴리스 노트 링크.

## 5. 금지 사항

- `main` 으로 직접 푸시 / force-push (분석 모드 문서 머지 제외, 제임스 사인오프 필수).
- **개발 모드에서** Jira 이슈 없는 코드 변경.
- 리뷰 없이 개발 통합 브랜치로 머지.
- 보안·성능 회귀가 발견된 PR 의 강제 머지.
- `--no-verify`, `--force` 등 우회 옵션 사용(명시 요청 없을 시).
- 하나의 PR 에 여러 태스크 묶기.
- 분석 모드에서 운영 코드 직접 수정.

## 6. 분석 모드 워크플로 (공통 가이드)

> 코드를 변경하지 않고 산출물(문서·표·다이어그램)만 만든다. 롤별 상세 단계는 각 롤 파일을 참조한다.
>
> **종합 분석 요청은 제임스 단독 작성 금지.** 제임스는 5명(네이선·정민·카맥·수영·수진) 에게 `team-send` 로 분담 위임 후 검수·통합만 수행. 단일 관점("보안만") 또는 단순 상태 조회("진행률만") 만 예외.

1. **스코프 선언** — 한 문장으로 적는다 (예: "결제 모듈의 보안·성능 audit").
2. **목적·이해관계자·종료 기준** 을 1 페이지로 정리.
3. **선행 자료 수집** — 기존 `docs/` 트리 + 코드베이스 인벤토리 (수진 담당).
4. **롤별 분석 수행** — 네이선(구조), 정민(보안·품질), 카맥(성능), 수영(UI/a11y), 수진(인벤토리·의존성). 제임스가 5명에게 `team-send` 로 동시 분담 위임.
5. **산출물 통합** — 수진이 `docs/analysis/index.md` 에 등재. 제임스가 5종 검수(스코프/형식/누락/품질/정합) 통과 후 `docs/diagnostics/state-of-system.md` 에 종합.
6. **사인오프** — 제임스가 산출물 묶음을 승인하고, 후속 개발 모드 전환 여부를 결정.

## 7. 순환 검증 구조 (Cyclic Verification)

> 단일 게이트가 아닌 다단계 체크포인트와 주기적 루프로 품질을 지속적으로 유지한다.

### 7.1 Per-PR 검증 파이프라인 (개발 모드)

**일반 dev 브랜치 PR (대부분의 경우)** — 제임스 SKIP.

```
마크 (구현 + 자가 테스트, TDD)
   │
   ├──→ 정민 (코드 리뷰 + 보안 체크리스트)    ← CRITICAL/HIGH 발견 시 마크 반려
   └──→ 카맥 (perf budget + 회귀)             ← perf budget 초과 시 마크 반려
        (정민·카맥 동시 병렬 검토)
   ↓
[정민 AND 카맥 모두 통과]
   ↓
(인터페이스 변경 PR 만) → 네이선 (아키텍처 정합성)
   ↓
**dev 브랜치 머지 — 제임스 사전 승인 불요**
```

**main 머지 PR (릴리스 시점만)** — 여기서만 제임스 진입.

```
dev 브랜치 (모든 Sub-task 완료) → 제임스 (릴리스 사인오프) → main 머지 + 태그
```

- 각 단계는 **명시적 통과·반려** 코멘트를 남긴다.
- 반려된 PR 은 사유와 함께 1단계 (마크) 로 돌아간다.
- 정민·카맥은 동시 병렬 검토 (둘 다 통과해야 dev 머지).
- **제임스는 일반 dev PR 에 끼어들지 않는다.** 코드 리뷰·perf 검증은 정민·카맥이 자율 수행. 제임스 진입 시점은 (a) dev → main 릴리스 결정, (b) 정민·카맥 사이에서 조정이 필요한 충돌 발생, (c) CRITICAL 보안 이슈 보고 — 세 가지뿐.
- **마크는 PR 완료 시 정민과 카맥에게 병렬 `team-send` 송신**한다. 원 발신자(제임스 등) 에게는 양쪽 통과 후 "상태 보고" 만 전달 (승인 요청이 아님).

### 7.2 주기적 검증 루프

| 주기 | 담당 | 활동 | 산출 |
|---|---|---|---|
| 주간 | 정민 | dead code · 의존성 CVE 스캔 | `docs/qa/review-log.md` 부록 |
| 주간 | 카맥 | 성능 회귀 대시보드 검토 | `docs/performance/regression-perf.md` 갱신 |
| 월간 | 네이선 | 아키텍처 드리프트 (현행 docs vs 코드) 점검 | `docs/analysis/system-map.md` 갱신 |
| 월간 | 수진 | 외부 의존성 풍경·신규 대안 조사 | `docs/analysis/dependency-audit.md` 갱신 |
| 월간 | 수영 | UI 인벤토리·a11y 회귀 점검 | `docs/analysis/ui-inventory.md` 갱신 |
| 분기 | 제임스 | 현황 진단 메모 + 로드맵 재조정 | `docs/diagnostics/state-of-system.md` 갱신 |

### 7.3 자동 피드백 루프

- 카맥의 perf 회귀 알람 → 마크에게 Jira 자동 생성 (개발 모드 진입).
- 정민의 커버리지 하락 알람 → 마크에게 테스트 보강 요청.
- 수진의 CVE 발견 → 네이선에게 의존성 교체 의사결정 요청.
- 네이선의 아키텍처 드리프트 발견 → 제임스에게 보고, 리팩터링 우선순위 후보로 등록.

## 8. 페인 간 메시지 전달 (Pane-to-Pane Messaging)

> 팀원 간 위임·질의·회신은 **`team-send` 헬퍼**를 통한 tmux 페인 주입으로 표준화한다. 사용자가 메시지를 수동 중계할 필요가 없다.

### 8.1 페인 매핑 (고정)

| 페인 | 역할 | 한국명 | 영문 alias |
|---|---|---|---|
| 0 | CTO | 제임스 | james, cto |
| 1 | Architect | 네이선 | nathan, architect |
| 2 | Developer | 마크 | mark, developer, zuck |
| 3 | UI/UX | 수영 | design, designer |
| 4 | Researcher | 수진 | sujin, researcher |
| 5 | QA·Reviewer | 정민 | qa, reviewer |
| 6 | Performance | 카맥 | perf, performance, carmack |

### 8.2 송신 (team-send 헬퍼)

**중요 — 호출 방식**: `team-send` 는 **반드시 Bash 도구로 실행한다**.
- ✅ 올바른 호출: `Bash("team-send 마크 'ADR-014 1단계 부탁'")`
- ❌ **금지: `Task(subagent_type="마크", ...)` 같은 sub-agent spawn 호출.** 팀원은 sub-agent 가 아니라 **별도 tmux 페인의 독립 Claude 인스턴스**다. Task 도구는 정민·마크 등을 찾을 수 없다.
- ❌ **금지: 응답 텍스트에 명령어를 적기만 하는 것.** `team-send ...` 를 자연어 응답으로 출력하면 실행되지 않는다. 반드시 Bash 도구 호출.

```bash
# 한 줄 메시지
team-send 마크 "ADR-014 의 1단계(SessionStore + 미들웨어 교체) 부탁합니다. 기한 5/19."

# 파일에서 읽기 (긴 위임 지시서·산출물)
team-send 네이선 -f docs/decisions/2026-05-14-multi-pg.md

# stdin 으로 파이프
cat report.md | team-send 제임스
```

헬퍼는 자동으로:
- 발신자(현재 페인) 를 식별하여 `[From: 제임스 → 마크] 2026-05-14 10:15` 헤더 부착
- bracketed paste 로 멀티라인 메시지를 한 청크로 안전하게 전달
- 마지막에 Enter 를 눌러 수신자 Claude 가 즉시 처리하도록 함
- 수신자 페인이 비활성(Claude 종료) 이면 exit 4 로 거절

`--no-header` 로 헤더 생략, `--session <name>` 으로 비기본 세션 지정 가능.

### 8.2.1 송신 후 검증 (의무 — 모든 크기 메시지 공통)

`team-send` 호출 후 **반드시 다음 4단계 확인**한 뒤에야 "전달 완료" 보고:

1. Bash 도구의 **종료 코드 = 0** (셸 출력 마지막 줄 `✅ <발신> → <수신> (pane N)`)
2. 비0 종료 시 stderr 메시지로 원인 식별 (exit 3 = 페인 없음, exit 4 = 비활성)
3. **수신자 페인 capture 으로 메시지 전달 확인** (`tmux capture-pane -t <session>:<window>.<pane> -p | tail -15`) — 메시지 본문이 페인 화면에 표시되어야 함
4. **Enter 발동 확인** — 수신자 페인 footer 영역에 `esc to interrupt` 또는 spinner (`✻ Thinking…` / `Crunched for Ns` 등) 표시되어야 active processing. 표시 없이 input prompt `❯ ` 영역에 메시지 잔존이면 **Enter 미발동** — 즉시 `tmux send-keys -t <session>:<window>.<pane> Enter` 으로 보강

검증 없이 "전달 완료" 응답 금지 — LLM 환각으로 거짓 보고가 발생함. **모든 메시지 크기 공통** (이전 3KB+ 한정 표준 → 전체 적용 강화, CEO 결정 2026-06-08).

**자동화 보완 — `team-send-verify` PostToolUse Hook (2026-06-09 도입)**:

- 본 repo `bin/team-send-verify.sh` 가 매 `team-send` 호출 직후 위 3·4 단계를 자동 수행 (capture-pane + 단일 패턴 활성 판정 + Enter 보강).
- Hook 가 spinner 미확인 시 자동 Enter 보강 → 재확인 → 그래도 미활성이면 stderr 진단 가이드 + exit 2.
- **Esc 자동 발사 등 destructive 동작은 절대 수행 안 함** — 페인의 사용자 작업 보호 (정민 권장 S6 β + CTO §14.5).
- 발동 로그: `/tmp/team-send-verify.log` (tail -20 로 최근 이력 확인).
- **Hook 도입 후에도 본 §8.2.1 4단계 의무는 유효** — Hook 는 보완책이지 면제책 아님. Hook 실패 (jq 미설치 / tmux 비가용 / 스크립트 손상) 시 매뉴얼 검증 fallback.
- 가이드: `~/.claude/skills/team-send-verify/SKILL.md` (자동 배포) — 디버그·비활성화 절차 포함.

### 8.2.2 Enter 미발동 사고 패턴 (학습 기록)

`team-send` 헬퍼는 bracketed paste 후 자동 Enter 송신하지만, 다음 경우 미발동 발생:

- 메시지 크기 3KB+ (bracketed paste 처리 중 race condition)
- 수신자 페인 idle 직후 paste 시점 timing
- 본인 (CTO) 페인에서 사용자 직접 입력 잔존 + paste 충돌

→ 본 §8.2.1 4단계 검증 의무로 사고 회복 표준화. 사고 발견 시 즉시 `tmux send-keys Enter` 보강.

### 8.3 수신 규약

각 멤버는 자기 페인에 도착한 메시지의 **첫 줄**을 검사한다.

- `[From: <발신자> → <본인>] <시각>` 형식이면 **위임/질의** 로 인식하고 작업을 시작한다.
- 헤더가 없으면 사용자 직접 입력으로 간주한다.

### 8.4 회신 (의무, 화면 출력 ≠ 송신)

**핵심 원칙** — 응답을 본인 페인 화면에 출력하는 것만으로는 발신자가 결과를 모른다. 반드시 `team-send` 명령으로 발신자 페인에 실제 송신해야 도착한다.

**의무 — 다음 시점에 반드시 `team-send` 회신**:

1. 위임받은 작업 단계 완료 시 — 결과·다음 단계·블로커 보고
2. 위임받은 작업 중 결정 필요 시 — 승인 요청 (자기 페인에만 적고 idle 진입 금지)
3. 위임받은 작업 중 에러·차단 발생 시 — 즉시 진단 보고
4. 멤버 간 협업이 필요할 때 — 자기 페인 input prompt 에 자가 노트로 적지 말고 `team-send <대상>` 명령으로 실제 송신

```bash
team-send 제임스 "[결과] TECG-123 1단계 완료. PR #142, 리뷰 정민에게 요청."
team-send 카맥 "[질의] perf 회귀 1.5x 의심 — 베이스라인 재측정 협조 부탁드립니다."
```

**절대 금지**:

- 응답을 본인 페인 화면에만 출력하고 발신자에게 `team-send` 송신 없이 idle 진입 — **발신자는 결과를 모름**
- 협업 요청·메모를 본인 페인 input prompt 에 자가 노트로 입력하고 bash 실행 안 함 — **대상 페인에 도착 안 함 (stale)**
- 외부 영향 큰 단계 (commit/push/머지/외부 송신) 도착 시 사용자 확인 패턴으로 idle — 위임 지시서 범위 내 자율 진행 + 결과는 `team-send` 회신

### 8.4.1 응답 종료 전 검증 (의무)

본인 페인의 응답을 종료하기 전에 **반드시 다음을 자가 점검**:

1. 위임받은 발신자에게 진행 단계·결과·블로커를 `team-send` 으로 송신했는가?
2. 협업이 필요한 타 멤버에게 `team-send` 명령으로 실제 송신했는가? (input prompt 자가 노트 금지)
3. 송신 결과 `✅ <발신> → <수신> (pane N)` 종료 코드 0 확인했는가?

위 3가지 중 하나라도 누락 시 — 응답 종료 금지. team-send 송신 후 종료한다.

### 8.4.1.5 "영역" 단어 placeholder 금지 (절대 규칙)

한국어 응답에서 **"영역" 단어를 placeholder처럼 반복 사용 금지**. LLM 토큰 생성 폴백 패턴으로 가독성을 심각하게 해친다.

**금지 예시** (실제 발생 사례):
- ❌ "Linux 영역 영역 영역 영역 영역" → ✅ "Linux 운영 측면 / Linux 환경 / Linux 동작"
- ❌ "사고 영역 영역" → ✅ "사고 처리 / 사고 사례 / 사고 시점"
- ❌ "본인 영역 영역" → ✅ "본인 입장 / 본인 판단 / 본인 권장"
- ❌ "머지 영역 영역" → ✅ "머지 시점 / 머지 결과 / 머지 처리"

**적용 의무**:
1. 응답 작성 중 "영역" 단어 사용 시 즉시 구체적 명사로 대체 (부분 / 점 / 항목 / 단계 / 상태 / 시점 / 내용 / 사유 / 결과 / 측면 / 사항 / 분류 / 요인 / 경우 / 때 / 곳 / 시 / 후 / 전 / 측 / 쪽)
2. **응답 송신 직전 의무 점검**: 본문 전체에서 "영역" 단어 grep → 1개라도 발견되면 송신 금지, 정정 후 송신
3. 적절한 명사를 찾지 못하면 문장 자체 재구성 또는 해당 부분 삭제

**Why**: 2026-05-27 CEO 첫 지적 → 2026-06-09 재지적 (강도 강화: "널 지워버리기 전에"). 본 표준 등재 후에도 반복 위반 발생. placeholder 반복은 LLM 출력 결함 신호이며 CEO 책망의 직접 원인.

**Quoted reference 예외 (2026-06-09 네이선 자가 식별 + CEO 결재)**:
- ✅ 허용: 표준 문서 본문 (본 §8.4.1.5 자기 정의), 자가 점검 grep 명령, 표준 위반 인용 보고 (정민 review-log, 사고 보고 등)
- ❌ 금지: 일반 응답 본문 (모든 멤버 회신, 사용자 답변)
- 대체 표기: `Y-단어` / `placeholder 단어` / `금지 단어` / `해당 단어` 사용
- 메타 토론 (표준 정의 / 자가 점검 / 위반 보고) 외 모든 본문에서 placeholder 자체 표기 회피

### 8.4.2 메시지 구성 ≠ 실행 (절대 금지 패턴)

**핵심**: `team-send` 메시지를 페인 출력 영역에 작성하거나 input prompt 에 입력만 하는 것은 **실행이 아니다**. 반드시 **Bash 도구 호출** 로 명령을 실행해야 대상 페인에 도착한다.

**금지 패턴 — 본 패턴으로 응답 종료 시 발신자는 결과를 영원히 모름**:

```
(잘못된 패턴 1) 응답 본문에 명령만 작성:
"다음으로 team-send 정민 '...' 송신하겠습니다." → 출력만 하고 Bash 호출 없이 종료

(잘못된 패턴 2) input prompt 에 명령만 작성:
페인의 ❯ prompt 에 team-send 명령 텍스트를 입력 + Enter 누르지 않은 채 응답 종료

(잘못된 패턴 3) 자가 노트:
"카맥에게 리뷰 요청 송신해줘" 같은 협업 메모를 page 어디에든 적고 실제 송신 안 함
```

**필수 패턴**:

```
1. Bash 도구 호출 시작 — command: 'team-send 정민 "[결과] ..."'
2. 도구 실행 완료 — 셸 출력 마지막 줄 `✅ <발신> → <수신> (pane N)` 확인
3. 종료 코드 0 검증 후 응답 종료
```

**근거**: 2026-06-05 사고 — 마크가 PR open 후 본인 페인에만 승인 요청 표시 + team-send Bash 호출 안 함 → CTO 5분 50초 누락. 정민·카맥·수진이 협업 요청·다음 액션을 본인 페인 input prompt 또는 출력 영역에 작성만 하고 Bash 도구 호출 없이 응답 종료 → 대상 페인에 도착 안 함 → CTO 가 "자가 노트 잔존" 으로 오판. 사용자 진단 (2026-06-05 09:36): **메시지 구성 후 실제로 엔터 처리·Bash 실행이 없는 것이 문제**. 본 표준은 모든 멤버 공통 의무.

### 8.5 브로드캐스트·다중 전달

`team-send` 는 1:1 만 지원. 1:N 이 필요하면 반복 호출.

```bash
for who in 네이선 마크 카맥; do
    team-send "$who" -f docs/decisions/2026-05-14-multi-pg.md
done
```

### 8.6 운영 주의사항

- 메시지는 수신자 Claude 의 **다음 프롬프트로 그대로 주입**되므로, 대화 중일 때는 약간의 컨텍스트 단절이 생길 수 있다. 위임 전 수신자 페인이 응답 대기 중인지 확인 권장.
- 인용 코드 블록, 백틱, 큰따옴표는 헬퍼가 bracketed paste 로 처리하므로 이스케이프 불필요.
- 매우 긴 메시지(> 8KB) 는 파일로 보내고 경로만 전달하는 패턴 권장 (`team-send 마크 "docs/guides/auth.md 참조"`).

### 8.7 사용자에게 메시지 전달을 부탁하지 않는다 (절대 규칙)

**팀 자동화의 핵심 원칙**: 사용자는 결정·승인 요청 대상이지, 메시지 중계자가 아니다.

`team-send` 가 실패해도 다음 순서로 자력 해결한다.

1. **명령어 재확인** — 수신자 이름·따옴표·파일 경로 오타 점검.
2. **수신자 페인 상태 진단**:
   ```bash
   tmux list-panes -t "$(tmux display-message -p '#S'):0" -F "#{pane_index}: #{pane_title} cmd=#{pane_current_command}"
   tmux capture-pane -t "<session>:0.<idx>" -p | tail -10
   ```
   - `pane_current_command` 가 `bash`/`zsh` 등 셸이면 Claude 가 종료된 비활성 페인. team-send 가 exit 4 로 거절함.
   - Claude 버전(예: `2.1.144`) 이 표시되면 정상 활성.
3. **재시도** — 일시적 응답 지연이면 잠시 후 재발송.
4. **그래도 해결 불가능 한 경우** — 사용자에게 보고하되 **다음 형식**으로만:
   - ✅ 허용: `[시스템 장애] <대상> 페인 비활성. 재시작 결정 요청드립니다.`
   - ❌ 금지: `사용자님이 대신 team-send 실행해 주세요`, `직접 전달 부탁드립니다`, `터미널에서 아래 명령 실행 부탁`

**근거**: 사용자에게 전달 대행을 요청하는 순간 자동화가 깨진다. 사용자가 손으로 옮긴 메시지는 발신자 추적·타임스탬프·정합성이 모두 끊긴다.

- **마크 (Developer)** — 브랜치 생성, 커밋, PR, Jira 상태 전환 / **단위·통합 테스트는 마크가 작성 (TDD 원칙)** / 분석 모드에서 finding note.
